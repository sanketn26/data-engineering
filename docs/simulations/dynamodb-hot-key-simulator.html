Why this matters

DynamoDB does not allocate throughput per logical item — it allocates it per physical partition, and a table's total provisioned or on-demand capacity is divided roughly evenly across however many physical partitions the table has. Every key hashes to exactly one physical partition. If traffic is skewed toward one logical key, all of that traffic lands on one partition and competes only against that partition's slice of the budget — not the table's total.

That is why ProvisionedThroughputExceeded throttling can appear on CloudWatch's per-partition (or Contributor Insights) view while the table-level consumed-capacity metric looks completely healthy — see DynamoDB, "Hot keys" and "On-demand is not a hotspot cure." A bigger bill without a key redesign does not fix a hot partition — raising total table throughput only raises every partition's budget by the same small amount; the hot partition is still absorbing nearly all the traffic alone.

  • Adding table-level capacity spreads the increase evenly across partitions the hot key never uses — it barely moves its own budget.
  • Sharding the hot key (e.g. appending a random suffix 0..N-1 and fanning reads/writes across it) spreads the same logical entity's traffic across N physical partitions, each getting its own budget.
  • This is a simplified model: real partition counts and hashing depend on table size, throughput history, and internal splits, and DynamoDB's adaptive capacity can reshape "hot" partitions over time — but it reacts on the order of minutes, not instantly, and has its own ceiling.
  • Watch throttles per partition, not average consumed capacity, when diagnosing this in production.
