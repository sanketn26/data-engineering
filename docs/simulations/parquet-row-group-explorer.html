Partitioning and row-group statistics are different mechanisms

This file has zero partitioning — there is no customer_id=.../ directory anywhere. All pruning shown above comes purely from footer min/max stats on row groups within a single file that was already opened. That is the distinction Parquet Internals makes explicit: partition pruning skips whole files using directory metadata before any file is opened; row-group statistics skip row groups inside a file you already decided to read.

  • Sorted before write: each row group's min/max becomes a tight, non-overlapping range, so a point filter matches roughly 1 of 8 row groups.
  • Unsorted (random order): each row group's min/max spans nearly the full 0-999 domain, so almost every row group's range contains the filter value and almost nothing gets skipped — even though the same footer stats exist.
  • Partitioning by date would not have helped this query at all — the filter is on customer_id, a column that was never a partition key. Sorting the write, not adding a partition column, is what makes this query cheap.
  • This is a planning estimate: real pruning also depends on page-level dictionary filtering and encoding, not modeled here.
