Why real clusters use this

Cassandra and DynamoDB both place partitions using a ring of hashed token ranges rather than hash(key) % N. That single design choice is what lets you add or remove a node without rehashing the entire dataset — see Cassandra for how tokens and vnodes map to replica placement, and DynamoDB for the same idea behind its partition key hashing.

  • With naive hash(key) % N, changing N changes the modulus for almost every key — a cache cluster doing this on scale-out would face a near-total cache miss storm.
  • On a plain ring with few physical nodes, ownership is lumpy: one node can land a disproportionate arc purely by chance. Virtual nodes spread each physical node across many small arcs, averaging out the imbalance — this is exactly what Cassandra's num_tokens setting controls.
  • Consistent hashing still isn't free: replication, hinted handoff, and repair after a node change are separate mechanics layered on top of placement — this simulator shows placement only.
  • The numbers here are illustrative (20 keys, a handful of nodes) — the ~1/N fraction becomes a much tighter guarantee at production key counts.
